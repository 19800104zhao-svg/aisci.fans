# AISci June 1 MVP

Original target launch date: 2026-06-01.

Status note updated on 2026-05-26: this document remains the baseline MVP scope, but the active public launch target for AISci.fans is now 2026-07-21.

This is the minimum acceptable version for AISci.fans to be meaningfully usable, not only presentational.

## Product Scope

The June 1 MVP must let a user answer these questions:

1. What are the most important scientific research problems right now?
2. What progress has already happened on each problem?
3. Which papers support that progress?
4. Which scientists and labs are relevant to the problem?
5. How can a young research-oriented user follow the problem, submit proof-of-work, and become visible?
6. How can a real scientist claim their profile?
7. How can the founder/admin review all user activity before anything sensitive becomes public?

## Must-Have User Flows

### Public Research Problem Query

- Browse/search curated research problems.
- Open a problem detail page.
- See problem summary, current progress, key bottlenecks, related papers, related scientists/labs, and source links.
- Filter by domain such as AI safety, AI biology, climate/materials, public health, robotics, energy, and science commercialization.

### Young Talent

- Register/sign in.
- Follow one or more research problems.
- Submit proof-of-work: paper replication, GitHub, notebook, dataset, essay, benchmark, experiment, or technical memo.
- See submitted work in a personal dashboard.
- Submit interaction requests or comments linked to a problem or scientist profile.

### Scientist / Profile Claim

- Scientist profile pages exist for relevant public researchers.
- A claimant can request ownership of a scientist profile.
- Claim evidence can include institutional email, ORCID, Google Scholar, lab website, passport/ID check, publication email, GitHub, or other strong evidence.
- Claim requests are private and pending by default.
- Founder/admin reviews and approves/rejects claims.

### Founder/Admin

- Admin can see all users, submissions, follows, problem records, scientist profiles, claim requests, and flagged content.
- Admin can approve/reject submissions and scientist claims.
- Admin can mark records public/private.
- Admin can export data if needed.

## Data Model Needed

Core tables/entities:

- `users`: account identity, role, admin flag, auth provider metadata.
- `research_problems`: title, domain, summary, bottlenecks, importance score, status.
- `problem_progress`: dated progress updates with source links and confidence.
- `papers`: title, authors, year, DOI/OpenAlex/arXiv URL, abstract/summary, problem links.
- `scientists`: name, affiliation, fields, profile URLs, source links, claim status.
- `problem_scientists`: scientist-problem relationship with evidence.
- `follows`: user follows a problem/scientist/lab.
- `submissions`: proof-of-work and user-submitted research outputs.
- `interactions`: comments, questions, collaboration requests, mentor requests.
- `claim_requests`: scientist profile claim evidence and review status.
- `admin_reviews`: audit log of admin decisions.
- `flags`: legal/privacy/safety/content flags.

## Auth And Database Decision

Recommended MVP backend: Supabase.

Reason:

- Supabase gives Postgres plus Auth in one system.
- Supabase Auth supports email/password, magic link/OTP, and social login providers including Google, GitHub, and Apple.
- Supabase integrates with Vercel and can provide environment variables to the Vercel project.
- Row Level Security can keep user submissions private by default while allowing founder/admin access.
- Supabase Studio gives a practical early admin data view before a custom admin UI is complete.

Alternative:

- Clerk + Neon is strong for polished auth and a separate Postgres database, but it adds one more vendor and more integration surface.
- The earlier custom email/password + Neon-compatible API was removed because custom auth is not the right path when Google/GitHub login and RLS are required by June 1.

Decision:

- Supabase is the implemented June 1 account/database path.
- The Vercel API verifies Supabase bearer tokens and uses the server-only service role for private/admin operations.
- The old custom Neon auth path was removed from the product code.

## Review And Verification Policy

Default visibility:

- User submissions: private/pending.
- Scientist claims: private/pending.
- Interactions with scientists: private/pending until an abuse/spam policy exists.
- Problem/paper/scientist source records: public only if sourced from public information.

Claim review should combine:

- Automated checks: email domain, ORCID URL, publication links, profile URL consistency, duplicate detection.
- Human founder/admin review for first version.
- Future expert review committee only after the workflow has real volume.

## Content Boundaries

AISci should not focus on:

- Political positioning or political persuasion.
- Regulated medical advice to patients.
- Dangerous biosecurity protocols, harmful wet-lab instructions, or actionable misuse guidance.
- Workflows that require legal, export-control, sanctions, securities, or compliance review before publication.

User-submitted information:

- Users may submit broad information.
- Registration and intake must warn users not to upload trade secrets, confidential third-party data, unpublished sensitive data, or content they do not have permission to share.
- Founder/admin can remove or keep private any submission that creates legal, privacy, safety, or reputational risk.
